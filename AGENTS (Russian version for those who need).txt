
# AGENTS.md

Руководство для разработчиков ИИ, работающих в этом репозитории.

## Обзор проекта

FitCalc — это приложение для планирования тренировок и питания. Репозиторий содержит две
связанных друг с другом частей:

- **FitCalc** — веб-приложение на FastAPI, предназначенное для пользователей (HTML-форма + REST API), которое
  возвращает план тренировок для выбранного уровня подготовки.
- **FitAI** — «интеллектуальный» модуль (`fitai/`), предназначенный для персонализации
  тренировок и питания на основе профиля пользователя, истории тренировок, дневника питания и
  истории веса, при необходимости с использованием модели ONNX с резервным вариантом на основе правил.

Это **студенческий семестровый/курсовой проект** (курс «Программная инженерия»), а не
продукт для коммерческого использования. См. `disclaimer.md`. Большая часть документации для пользователей написана на
русском языке (`README.md`, `tz.md`, `docs/*.md`, `fitai_docs/*.md`), тогда как код, строк документации
и идентификаторы — на английском языке.

## Технологический стек

- Python 3.11, FastAPI, Uvicorn, Jinja2, Pydantic v2
- SQLAlchemy 2.x + Alembic (сохранение данных в SQLite для модуля FitAI)
- `onnxruntime` + `numpy` (необязательно; файл модели не включается в репозиторий)
- `matplotlib` (построение графиков для лабораторных демонстраций), `httpx` (тесты), `unittest` (без pytest)

## Структура проекта

```
fitai/
  domain/           Замороженные классы данных (models.py) и контракты хранения (repository.py)
  application/      FitAIController, порты сервисов (Protocols), модули принятия стратегических решений,
                    построители планов тренировок
  infrastructure/   адаптер вывода ONNX, ORM/репозиторий SQLAlchemy, преобразователи данных,
                    инициализация БД/миграции, буферизованный записыватель метрик
  web/              Фабрика приложений FastAPI (app.py), REST API (api.py), шаблон Jinja2
  lab4_demo.py      Демонстрация персистентности/метрик (симулированное, а не реальное вычисление)
migrations/         Миграции Alembic (схема SQLite для модуля FitAI)
tests/              Набор тестов unittest (обнаружен в корневом каталоге репозитория)
docs/               Отчёты по лабораторным работам (LAB5.md, LAB7.md)
fitai_docs/         Документация по проектированию FitAI, диаграммы PlantUML, отчет по lab4
```

## Общие команды

Все команды запускаются из корневого каталога репозитория.

```bash
# Настройка
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

# Запуск веб-приложения (для формы плана/API не требуется база данных, учетная запись или модель ONNX)
python -m uvicorn fitai.web.app:app

# Запустить полный набор тестов
python -m unittest discover -s tests -v

# Запустить демонстрацию сохранения данных из лабораторной работы № 4 (100 итераций, выводит график FPS/памяти)
python -m fitai.lab4_demo --iterations 100 --plot fps_vs_gc.png
# ...с изолированной базой данных:
python -m fitai.lab4_demo --database /tmp/fitai-lab4.sqlite3
```

`onnxruntime` и `numpy` требуются только для запуска реальной модели ONNX и отсутствуют в
`requirements.txt`. Файл модели ONNX намеренно не включён в репозиторий; веб-приложение и
тесты работают и без него.

## Архитектура и соглашения

Модуль `fitai` построен по многоуровневой (чистой) архитектуре с инъекцией зависимостей:

- **Доменный уровень** (`fitai/domain/`) содержит простые замороженные классы данных
  (`FitnessUserContext`, `WorkoutPlan`, `InferenceResult`, `AiAgent` и т. д.) и
  контракты хранения на основе `Protocol`. Он не должен зависеть от FastAPI, SQLAlchemy или
  ONNX.
- **Прикладной уровень** (`fitai/application/`) определяет **порты** сервисов как
  `typing.Protocol` в файле `ports.py`. `FitAIController` координирует работу провайдеров, формирование
  построение признаков, инференс, принятие решений, питание и форматирование; он принимает всех
  участников в качестве аргументов конструктора, доступных только по ключевому слову, и никогда не создаёт их самостоятельно.
- **Шаблон «Стратегия»**: `IWorkoutDecisionMaker` реализуется
  `NeuralNetworkDecisionMaker` (использует выходные данные модели, делегирует результаты `None` правилам)
  и `RuleBasedFallback` (только правила). Оба удовлетворяют одному и тому же контракту `create_plan(context,
  result)», поэтому контроллер и `WorkoutPlanService` могут вызывать любой из них
  одинаково.
- **Уровень инфраструктуры** (`fitai/infrastructure/`) предоставляет адаптеры:
  `OnnxInferenceService` (один вход/один выход, владеет собственной сессией, менеджер контекста
  её закрывает), `SqlAgentRepository` + `data_mapper.py` (строки ORM <-> доменные модели),
  `db.py` (движок SQLite + миграция Alembic) и `BufferedMetricsWriter` (фоновый
  поток, который пакетно отправляет метрики в репозиторий).
- **Веб-уровень** (`fitai/web/`) предоставляет форму (`GET /`, `POST /`) и JSON-API
  (`GET /api/v1/experience-levels`, `POST /api/v1/workout-plans`). `create_app()` — это
  фабрика, которая собирает приложение с реализациями по умолчанию и принимает
  `WorkoutPlanService` для вставки в тестовый код.

Ключевые принципы проектирования, отражённые в коде и тестах:

- **Инверсия зависимостей** — контроллеры/сервисы зависят от `Protocol`, а не от конкретных
  классах.
- **ISP** — поставщики данных разделены на `IProfileProvider`,
  `ITrainingHistoryProvider`, `INutritionDataProvider` вместо одного «толстого» интерфейса
  (см. `tests/test_isp.py`).
- **LSP** — модули принятия решений взаимозаменяемы в рамках одного контракта.
- **Хранилища** — одна короткая сессия на каждую операцию; `SqlAgentRepository` управляет
  транзакциями и делегирует сопоставление строк файлу `data_mapper.py`.
- В схемах запросов API используется `extra="forbid"` (отклонение неизвестных полей).

## Тестирование

- Используйте встроенный фреймворк `unittest` (без pytest). Тесты находятся в каталоге `tests/` и
  обнаруживаются из корневого каталога репозитория.
- Тесты охватывают контроллер, модули принятия решений, адаптер ONNX, контракты ISP, веб-форму,
  REST-API и хранение данных в SQLite. При добавлении нового функционала придерживайтесь существующего
  стилю `unittest.TestCase` + `unittest.mock.Mock`.
- Приложение импортируется как `from fitai.web.app import app` (экземпляр на уровне модуля) и
  `create_app` (фабрика для встраиваемых сервисов).

## Примечания по данным и хранению

- Модуль FitAI использует SQLite. Путь к базе данных по умолчанию —
  `$XDG_DATA_HOME/fitcalc/fitai.sqlite3`, при отсутствии —
  `~/.local/share/fitcalc/fitai.sqlite3`. Для переопределения используйте `--database` (лабораторная демонстрация) или
  `initialize_database(path)`, чтобы переопределить его.
- Управление схемой осуществляется с помощью Alembic (`migrations/versions/0001_initial_schema.py`); примените
  с помощью `migrate_database` или `initialize_database`.
- `player_progress.inventory_json` намеренно хранит инвентарь в виде столбца JSON
  (документированное исключение из 1NF); если требуются запросы на уровне предметов, извлеките его в
  таблицу `inventory_items`.
- `BufferedMetricsWriter` необходимо закрыть (или использовать в качестве контекстного менеджера), чтобы очистить
  оставшуюся очередь; при принудительном завершении процесса могут быть утеряны буферизованные метрики.

## Язык и стиль

- Код, docstrings, комментарии и идентификаторы написаны на **английском** языке.
- Текст, предназначенный для пользователей, HTML-шаблоны и лабораторные/проектные документы написаны на **русском** языке.
- Новый код должен соответствовать существующей многоуровневой структуре и стилю `unittest`.
