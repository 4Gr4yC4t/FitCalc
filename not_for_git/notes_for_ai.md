# Что требуется по итогу (критерии оценки)

1. UML-диаграмма классов (PlantUML или draw.io) с интерфейсами, реализациями и стереотипами `<<interface>>`.
2. Рабочий код модуля на Python, где **каждый из 5 принципов SOLID обоснован конкретным участком кода**.
3. Внедрение зависимостей: никаких синглтонов и оператора «создания зависимости» внутри бизнес-логики — зависимости передаются снаружи (конструктор / Composition Root).
4. Корректное управление ресурсами (в C# это `IDisposable`, в Python — аналог: `with`/`.close()` для сессии ONNX).
5. Чёткое разделение слоёв: **Domain** (Blackboard, команды, рекомендации) / **Application** (FitAIController) / **Infrastructure** (OnnxInferenceService, FitCalcApiClient).
6. Пояснительная записка: для каждого принципа — определение, скриншот фрагмента UML, фрагмент кода и сценарий нарушения («что сломается, если принцип нарушить»).

## Шаги работы по этапам лабы

**Шаг 1. Анализ ТЗ и выделение сущностей (Этап 1 лабы, 0–30 мин)**
Возьмите разделы FitAI ТЗ («Границы системы», «Функциональные требования», «Архитектура») и разложите на 4 группы:
- **Входные данные:** профиль пользователя, цель, история тренировок, дневник питания, динамика веса;
- **Выходные данные:** план тренировки, рекомендации КБЖУ, предупреждение о перегрузке, объяснение факторов;
- **Процессы:** сбор признаков (FeatureBuilder), инференс ONNX, принятие решения (WorkoutDecisionMaker), форматирование (RecommendationFormatter);
- **Внешние зависимости:** ONNX Runtime, REST API FitCalc, (опционально) PostgreSQL.

**Шаг 2. UML Class Diagram (Этап 2, 30–90 мин)**
Строите диаграмму из вашего же ТЗ (раздел 6): интерфейсы `IFitnessDataProvider`, `IInferenceService`, `IWorkoutDecisionMaker`, `INutritionRecommendationService`, `IOvertrainingDetector`, `IRecommendationFormatter`, `IRuleBasedFallback`, `IFitCalcApiClient` и классы-реализации. Ключевое требование — стрелки зависимостей от `FitAIController` идут **к интерфейсам, а не к классам** (это DIP, это же проверяют на защите).

**Шаг 3. Ядро системы — SRP (Этап 3, 90–150 мин)**
Реализуете класс инференса так, чтобы он отвечал **только** за запуск ONNX-модели. В Python это скорее всего `onnxruntime.InferenceSession`, обёрнутая в класс `OnnxInferenceService`. Правило проверки: «если завтра формат модели изменится / добавится квантование — меняется один файл». Аналогично FeatureBuilder не принимает решений, только строит вектор признаков (у вас это прямо прописано в ТЗ, раздел «Принцип разделения ответственности»).

**Шаг 4. Центральный контроллер — OCP + DIP (Этап 4, 150–180 мин)**
`FitAIController` зависит только от абстракций (протоколы/ABC в Python), зависимости приходят через конструктор. Проверка ОСР: добавление новой стратегии принятия решений (например, стратегия для режима Профи с периодизацией) должно потребовать **новый файл + одну строку в Composition Root**, ноль правок внутри контроллера.

**Шаг 5. Взаимозаменяемость стратегий — LSP (Этап 5, 180–210 мин)**
Самое естественное место в вашем проекте — **пара `NeuralNetworkDecisionMaker` / `RuleBasedFallback`** (это прямо ваш FR-11): оба реализуют `IWorkoutDecisionMaker` с идентичным контрактом, и в Composition Root можно подменить нейросеть правилами без правки `FitAIController`. В записке фиксируете: «замена инстанса не ломает Update/BuildRecommendation».

**Шаг 6. Разделение «жирных» интерфейсов — ISP (Этап 6, 210–240 мин)**
Нужно найти в своём коде интерфейс, который заставляет реализацииции имплементировать лишнее, и разделить его. В вашей предметной области очевидный кандидат — `IFitnessDataProvider`: контроллеру нужен профиль + история тренировок, а вот данные питания и взвешиваний нужны только `NutritionRecommendationService` и аналитике. Разделение на `IProfileProvider` / `ITrainingHistoryProvider` / `INutritionDataProvider` — готовый пример рефакторинга «было/стало» (в лабе он требуется явно).

**Шаг 7. Отчёт и демонстрация (Этап 7, 240–270 мин)**
- Экспорт финальной UML-диаграммы.
- Пояснительная записка по шаблону: 5 принципов × (определение + скрин UML + код + сценарий нарушения). Примеры сценариев под ваш проект: нарушение SRP → при смене ONNX на TFLite правится половина модулей; нарушение ОСР → добавление голосовых/профи-стратегий требует переписывания контроллера; нарушение DIP → невозможно подменить инференс моком в тестах.
- Демонстрация работоспособности: в точке входа (Composition Root, например `main.py` или фабрика в FastAPI) меняете **один параметр** — с реальной ONNX-модели на fallback — и показываете, что рекомендации продолжают формироваться без изменения ядра.

## Что учесть из оговорок самой лабы

- Обучать нейросеть **не нужно** — разрешена заглушка: ONNX-модель-заглушка, хардкоженный вектор выходов или `DummyInferenceService` с задержкой ~20 мс. Архитектура важнее, чем модель.
- Критерий «нет оператора new в бизнес-логике» в Python трактуется как: никаких `OnnxInferenceService(...)` / `requests.post(...)` внутри контроллера — только инъекция.
- «Не блокировать главный поток» → если сделаете эндпоинт FastAPI, инференс выносится в `async def`/тред-пул, это заодно закроет ваше же нефункциональное требование из ТЗ (500 мс, потокобезопасность).

## Что можно «навайбкодить», а что лучше сделать самим (моё мнение, решать вам)

- **Самим:** диаграмма классов (Шаг 2) и пояснительная записка (Шаг 7) — на защите препод почти наверняка спросит «почему стрелка сюда», и отвечать придётся по схеме, которую понимаете вы.
- **Вайбкодить можно:** каркас классов по готовой диаграмме (Шаги 3–6) и заглушки-сервисы — это механическая работа, а критерий приёмки (компилируется/работает без падений, тесты) легко проверить запуском.
